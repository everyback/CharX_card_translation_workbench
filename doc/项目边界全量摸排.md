# Card Translation Workbench 项目边界全量摸排

- 审计日期：2026-09-03
- 审计对象：当前源码、配置、测试、README、产品体验文档、Git 历史，以及与本项目相关的历史工作记录。
- 审计性质：这是产品和工程边界清单，不是安全认证，也不是端到端部署验收。

## 1. 本次纠正后的核心结论

用户所说的“后面追加了 Lua 检测流程”，重点不是强行增加一个独立的 Lua 主流程，而是：

> 保存按钮必须把卡片工作过程中所有已经产生、并且满足保存条件的卡片工件修改一起保存。Lua 只是其中一个修改来源。

因此，保存的正确语义是“工作稿聚合提交”，不是“保存最后打开的页面”，也不是“把所有数据库字段都写进卡片”。

保存后的卡片工作稿应当等价于：

    原始工件
    + 已批准的卡片/世界书/问候语/可见文本段落
    + 已批准的模块文本段落
    + 当前模块草稿中已明确写入的 Lua、正则、运行时别名、路由修复等修改
    + 已确认的资源 JSON 修改
    + 已确认的图片替换
    + 需要同步的容器镜像（例如 CHARX 的 card.json 与 module.risum）

但以下内容不能因为点击保存就进入卡片：

    未审核或未确认的候选、仅预览结果、任务日志、模型设置、术语表、
    扫描统计、协议发现元数据、界面导航状态和外部平台写入。

这条定义同时解决两个常见误读：

1. 保存不能漏掉在其他页面已经确认的修改，例如 脚本管理页直接写入的模块草稿。
2. 保存所有流程修改不等于把所有配置、日志和候选数据混成卡片内容。

### 1.1 从示例抽象出的边界判定方法

用户给出的两个例子实际上指向同一类问题：系统已有一个对外承诺，后续新增代码不能只在局部成立，必须回到完整生命周期检查。今后发现需求时，先把它归入下面的边界维度，再决定改哪个模块：

| 示例中的要求 | 抽象出的边界 | 必须检查的所有位置 |
|---|---|---|
| 固定配置不能缩小或扩大 | 值域、默认值、单位、空值语义和作用范围不可漂移 | 设置页、API schema、数据库迁移、调度器、恢复、导出命名、测试 |
| 新增流程不能被快速指引跳过 | 流程拓扑和完成条件是产品契约 | 向导步骤、快捷入口、任务状态、保存、导出、失败重试、恢复 |
| 保存要收拢其他流程的修改 | 工件修改必须有统一归属和聚合提交点 | 卡片、世界书、模块、资源、图片、容器镜像、UI 保存、API 保存 |
| 已审核和仅有候选不能混淆 | 状态转换必须决定写入资格 | candidate、draft、confirmed、approved、force-pass、ready |
| 原文和译文结构不能被破坏 | 内容边界与结构边界分离 | 占位符、宏、正则、路径、ID、协议壳、模板、保护检查 |
| 导出不能代替保存 | 持久化、下载和外部写入是三个不同动作 | 保存、保存并导出、导出、远端同步、回退 |
| 清空不能误伤其他修改 | 破坏性动作必须声明完整影响面 | clear-results、rescan、delete、备份、撤销和恢复 |

因此，“新增一个按钮能跑通”不算完成；只有每个入口、状态和失败路径都遵守同一边界，才算接入项目工作流程。

## 2. 历史依据和审计范围

项目目录没有保存一份可直接查询的 Codex 对话数据库。因此本次历史核对使用了：

- Git 提交历史，重点检查资源 JSON、OCR/图片、审核、Lua 阶段和 CHARX 同步相关提交。
- README.md、README.en.md 和 docs/产品体验提升计划.md。
- 与本项目关联的历史工作记录：独立工作台、可选翻译范围、人工对比审核、世界书覆盖和 CHARX 双文件同步要求。

历史上已经确认的产品约束：

- 工作台独立调度模型，不以 RisuAI 或 BTB 作为核心运行依赖。
- 翻译范围由可选择的范围控制，结果必须经过原文/机器译文/人工定稿对比和审核。
- 世界书是正式翻译范围，不能因为它不在普通角色字段里就遗漏。
- 世界书原触发词、结构键、ID、常量标志和正则规则要保留；目标语言别名只能追加。
- CHARX 导出必须同时保持卡片 JSON 和嵌入的 module.risum 一致。
- 原卡片不直接覆盖，保存的是项目内审核稿；导出是下载，不等价于远端回写。

## 3. 状态模型：什么是卡片，什么不是卡片

| 状态层 | 当前代表 | 是否属于保存按钮的卡片工件 |
|---|---|---|
| 原始快照 | original_json、original_module_json、source_blob/source storage | 只读基线，不能被普通保存覆盖 |
| 工作元数据 | scope、语言模式、任务、日志、协议 schema、扫描统计、术语 | 不写进卡片；分别持久化 |
| 翻译/审核候选 | segments.translated_text、final_text、review_status、included | 只有满足批准门槛的段落才能进入工作稿 |
| 直接工作稿 | draft_json、draft_module_json、draft_source_blob/storage | 属于卡片工件；保存时必须保留并与批准段落合并 |
| 资源候选 | OCR 候选、AI 图片替换候选 | draft 不能进入卡片；confirmed 也必须有明确的资源应用通道 |
| 导出文件 | JSON、PNG、CHARX、RISUM 下载响应 | 只从已保存工作稿生成，不反向修改原始快照 |
| 外部平台 | RisuAI、SillyTavern 或其他远端服务 | 当前项目不由保存或导出自动写入，必须另有明确授权和入口 |

### 3.1 原始快照边界

导入时保存的原始 JSON、原始模块和源文件哈希是回退和比较依据。普通扫描、翻译、审核、保存、导出不能覆盖它们。

如果某个结构修复确实必须改变比较基线，不能悄悄改写 original_*；应当创建有版本号、前后哈希、原因和操作者的“修复后基线”。路由修复属于翻译稿修改，只能写入 draft_module_json；原始模块始终保持导入时的基线。

### 3.2 工作稿边界

工作稿是可继续编辑、可保存、可导出的卡片版本。保存必须以当前工作稿为基础，而不是每次只从原始卡片重新拼装，否则其他页面已经做出的直接模块修改会丢失。

### 3.3 候选和批准边界

模型结果、OCR 结果、AI 图片结果、正则分析结果都是候选。候选“存在”不代表“允许写入卡片”：

- 文本和模块段落：必须有非空最终文本且 review_status 为 approved。
- 图片替换：必须是 confirmed，且有可读的候选文件。
- OCR：confirmed 只表示人工确认 OCR 文本；除非存在明确的图像重绘/资源 JSON 应用通道，否则不能宣称已经保存到卡片。
- 正则 force-pass：只记录对当前模式和命中数差异的精确人工放行，不等于正则已被翻译，也不关闭其他完整性检查。

## 4. 修改来源全量清单

下表是保存按钮必须遵守的“修改通道清单”。新增任何通道都必须补到这里。

| 修改来源 | 实际存储 | 保存时的处理 | 当前边界 |
|---|---|---|---|
| 卡片普通字段 | segments，路径指向 card JSON | approved 后应用到 draft_json | 保留协议壳、占位符和受保护结构 |
| 世界书正文/名称/注释 | segments | approved 后应用 | 世界书属于正式范围，不能被普通范围默认逻辑遗漏 |
| 世界书目标语言别名 | lorebook-key-alias segment | approved 后追加到既有 keys/secondary_keys | 原键、ID、constant、regex 标志不替换 |
| 问候语和可见脚本文本 | segments | approved 后应用 | 只改可见文字，不改变量、函数、宏、URL、代码结构 |
| 模块中的可见 Lua 文本 | Lua 文本 segments | approved 后应用到模块草稿 | 受保护的 Lua 代码和结构不能按普通文本覆盖 |
| Lua 语法行人工修复 | 直接写 draft_module_json | 保存时以当前 draft_module_json 为基础继续合并 | 只改指定整行，使用路径/行号/旧行防止过期覆盖 |
| Lua 正则覆盖候选/人工规则 | draft_module_json，另有 validation overrides | 已显式保存的模块改动必须保留；预览不算改动 | 编译、命中集、结构和 force-pass 仍要独立校验 |
| 运行时名称别名 | 直接写 draft_module_json | 保留追加结果 | 只能追加目标语言别名，不能改 ownerId、资源名或原目录 |
| 头像路由修复 | 直接写 draft_module_json | 必须保留已确认修复 | 不得改写 original_module_json，也不得借修复入口自动修改未选择的 Lua |
| CHARX 资源 JSON 可见文本 | resource segments | approved 后改写对应归档条目 | 只在完整解析且条目存在时应用 |
| AI 图片替换 | resource_image_candidates + 独立 storage 文件 | confirmed 后替换草稿源包中的对应资源 | draft 图片必须排除；资源路径和格式必须匹配 |
| OCR 文字 | resource_ocr_candidates | 当前没有直接写回图片或资源 JSON 的应用步骤 | confirmed 不能被 UI 误报为已进入导出；若产品要落盘必须新增明确转换通道 |
| 术语表 | glossary_terms | 不进入卡片；只影响模型请求 | 术语的新增/删除不能改变已有卡片文字 |
| 语言模式、源/回退/目标语言 | projects/settings | 不进入卡片正文；影响扫描、QA、提示词和命名 | 取值、默认、空值和 preserve/target 语义不可擅改 |
| 范围选择 | projects.scope | 只决定扫描/翻译候选范围 | 不能改变保护、审核、保存和导出门禁 |
| 协议发现/分析/规则 | protocol schema/occurrence | 不直接写卡片；作为扫描和保护规则输入 | 分析结果不是用户批准的正文译文 |
| 任务、批次、日志、重试 | jobs/job_items/job_logs | 不进入卡片；保存后仍须可追溯 | 任务状态不能冒充卡片工件版本 |
| 扫描重连 | segments 的身份匹配和 obsolete 删除 | 不直接改工作稿；但会影响以后哪些段落可保存 | 删除旧段落前必须显示范围和可恢复信息 |

## 5. 保存按钮的强制契约

### 5.1 聚合顺序

保存必须采用一个可说明、可重复的聚合顺序：

1. 读取当前项目版本、原始快照、当前 draft_json、当前 draft_module_json 和 draft source。
2. 读取全部修改通道及其状态，不只读取当前页面的状态。
3. 以当前直接工作稿为基础，合并满足批准条件的卡片/模块段落。
4. 以当前草稿源包为基础，合并已批准资源 JSON 和 confirmed 图片替换。
5. 对 CHARX 同步 card.json 与 module.risum 的世界书镜像。
6. 执行保护片段、协议壳、模板、控制引用、Lua 语法、正则覆盖和格式完整性检查。
7. 所有必需写入成功后，才一次性更新草稿路径、哈希、状态和更新时间。

禁止只做以下任一种不完整实现：

- 只用 original_json 重建草稿，覆盖已有 draft_module_json。
- 只保存审核段落，丢掉 Lua/正则/别名/路由等直接修改。
- 只保存当前页面选中的资源，忽略其他已 confirmed 的资源候选。
- 只写 card.json，忘记 CHARX 中的 module.risum。
- 把“有候选”“有预览”“任务完成”当成“可以写入卡片”。

### 5.2 包含和排除规则

保存的最小条件是“属于卡片工件 + 状态满足该通道的确认条件 + 路径和版本仍匹配”。

保存必须排除：

- review_status 不是 approved 的段落；
- included 明确为 false 的段落；
- draft 状态 OCR/图片候选；
- 只有 preview、analysis 或日志而没有显式保存动作的结果；
- 模型设置、术语表、协议 schema、任务日志和 UI 状态；
- 未经单独授权的外部平台写入。

当前实现的 applyApprovedSegments 和 applyApprovedResourceJson 主要按 approved 判断，未统一检查 included。若接口允许“included=false 且 approved”，保存可能把用户明确排除的段落写入草稿。这是必须修正或明确禁止的边界，不能靠界面默认值掩盖。

### 5.3 直接工作稿和段落修改的冲突

同一路径同时存在直接工作稿和段落批准结果时，必须有稳定规则：

- 模块：以当前 draft_module_json 为基底，再应用当前仍有效的 approved 模块段落。
- 卡片：不能覆盖用户已经存在的卡片级直接编辑；若未来增加卡片直接编辑接口，必须定义版本冲突和人工选择。
- 资源：以当前 draft source 为基底，重复保存必须幂等，不能反复压缩或叠加同一替换。

冲突、过期路径、源文本哈希不匹配时应返回明确的冲突结果，不得静默选择一个版本。

### 5.4 成功、失败和报告

只有全部必需校验和写入完成，项目才能进入 ready。保存响应和界面至少应能回答：

- 卡片、模块、资源 JSON、图片和镜像各应用了多少项；
- 哪些候选被排除，以及排除原因；
- 哪些 Lua/正则阶段仍失败、待重试或被 force-pass；
- 保存使用的项目版本、源哈希和草稿哈希；
- 保存失败时是否发生了部分落盘。

模型别名翻译失败、Lua 正则失败或资源条目无法解析，不能被写成“全部成功”。如果用户确认继续，必须把“带失败继续”的决定记录为显式结果。

## 6. 与保存相邻但不能混淆的操作

| 操作 | 正确语义 | 不得被误解为 |
|---|---|---|
| 扫描 | 根据范围从原始内容发现/重连段落和风险 | 保存翻译结果 |
| 翻译任务 | 产生机器候选并持久化任务进度 | 批准或导出 |
| 审核/批准 | 决定段落是否有资格进入工作稿 | 直接改源文件 |
| 保存 | 聚合所有符合条件的卡片工件修改，生成项目审核稿 | 只保存当前页，或写远端平台 |
| 保存并导出 | 先执行保存，再对已保存稿做导出门禁并下载 | 绕过审核或自动远端回写 |
| 导出 | 根据已保存工作稿生成 JSON/PNG/CHARX/RISUM | 把未保存候选临时拼进下载包 |
| 预览/分析 | 只读计算或模型建议 | 已经写入草稿 |
| force-pass | 对精确正则命中差异人工放行 | Lua 流程整体完成 |
| 清空结果 | 明确的破坏性重置 | 只清空当前页面的一条结果 |

## 7. 类似的跨流程边界

### 7.1 固定配置不能缩小或扩大

已经确认的配置项，其取值集合、默认值、单位、上下限、空值/0 语义、优先级和作用范围都是契约。包括：

- host/port、上传限制、数据库 worker 数；
- sourceLanguage、fallbackLanguage、targetLanguage、languageBehaviorMode；
- 并发、批量段落数、批量字符数、超时；
- all、core、standard、visible-scripts、all-visible、lua-only 等既有范围值。

快速预设、首次引导和高级设置只能显式修改用户可见的配置，不能后台缩小范围、扩大范围、改默认值或把 0/空值换成另一种业务含义。设置页、API 校验、数据库、调度器和重启恢复必须使用同一套语义。

### 7.2 范围选择不能变成安全旁路

范围只决定“哪些自然语言候选要翻译”。它不能关闭：

- 原始快照保护；
- 世界书结构和触发词保护；
- Lua/正则/协议/模板完整性检查；
- 审核门槛和资源确认门槛；
- 保存聚合和导出前检查。

例如 core 范围可以不产生 Lua 文本译文，但检测到模块后，保存仍必须保留已有模块草稿，并执行适用的结构检查。

### 7.3 新增流程的接入不是新增按钮

以后增加检测、修复、审核、资源处理或同步流程，必须先定义一个“修改通道契约”：

1. 修改的卡片工件路径或说明它只是元数据；
2. candidate/draft/confirmed/approved 等状态；
3. 何时写入 draft_json、draft_module_json 或 draft source；
4. 保存是否必须聚合它；
5. 失败、重试、取消、重扫和清空时如何处理；
6. 哪些检查会阻断保存或导出；
7. UI、直接 API 和任务恢复是否使用同一规则。

只有独立页面和独立 API、没有保存聚合和门禁定义的流程，视为未完成接入。

特别是新手快速指引：它可以减少用户选择，但不能制造一条绕过正式阶段的隐藏路径。新增阶段必须在快速指引、普通工作台、任务恢复和保存并导出中具有同等的状态含义；如果该阶段产生卡片工件修改，最终保存必须能读到它，即使用户没有再次打开对应页面。若某阶段只做检测而不产生工件修改，也必须在完成条件和导出门禁中明确记录“已检测/未修改”，不能用页面跳过来伪造“已完成”。

### 7.4 保护结构和翻译文本分离

变量名、函数名、CSS 类、宏、URL、资源路径、正则控制结构、协议壳、按钮动作 ID 和脚本引用默认不是可翻译文本。可见文字可以翻译，但必须在占位符保护、恢复和完整性检查后才可批准。

世界书原触发词不能被译文替换。目标语言别名是追加数据，不是删除原键。

### 7.5 容器镜像同步

CHARX 的 card.json 与 module.risum 是同一张卡的两个相互关联表示。任何一侧的世界书或模块变化，都必须在保存/导出时同步另一侧；只改一个文件即视为不完整工件。

RISUM 的模块资源、CHARX 的普通归档资源和嵌入模块资源也必须使用对应容器路径，不得把包内逻辑路径当作操作系统路径。

### 7.6 预览、显式保存和自动后处理

模型分析、正则 coverage preview、路由 repair preview、资源 inspection 只读。只有显式应用、确认或保存接口才可以改变工作稿。

自动后处理如果会改变模块草稿，必须：

- 明确写入哪个草稿字段；
- 记录数量、失败和重试状态；
- 在保存时保留这些改动；
- 不因计数为 0 就假定阶段完成；
- 失败时不伪造 ready。

### 7.7 破坏性操作的范围

删除项目、清空结果和重扫都可能影响多个修改通道：

- clear-results 只清除翻译段落结果，并将卡片正文草稿和资源草稿恢复到原始值；它不得重置 draft_module_json。Lua 草稿必须由 Lua 页面自己的“恢复原始 Lua 草稿”按钮单独处理，且该按钮不得修改卡片正文、资源草稿或 original_module_json。
- rescan 会按身份重连段落，并删除未匹配的旧段落；必须展示 scope、保留数和 obsolete 数。
- delete 会删除项目数据库和项目 storage，当前没有回收站。

按钮文案和确认框必须明确这些跨通道后果，并在可行时先提供备份或导出。

### 7.8 并发和快照

保存必须针对一个稳定项目版本。活动翻译任务、Lua 直接编辑、资源确认和保存不能互相覆盖：

- 要么保存拒绝 queued/running/paused 任务；
- 要么采用项目版本号/乐观锁，在版本变化时返回冲突；
- 不能只依赖前端按钮 disabled，因为直接 API 仍可调用。

当前 apply 路由主要检查语言和保护问题，未看到统一的活动任务快照门禁；这是发布前必须补测的风险。

### 7.9 API、界面和恢复路径一致

顶部保存、向导保存、保存并导出、脚本管理页触发的安静保存、直接 POST /apply 和任务恢复，必须使用同一个保存聚合器和同一套门禁。任何入口都不能因为“快捷”“内部”或“重试”而少合并一个修改通道。

## 8. 当前代码核对结果

### 已有的正确方向

- export-service.applyProject 会读取全部 segments，并分别处理卡片、模块和资源路径。
- 模块应用以现有 draft_module_json 优先作为基底，能够保留 Lua 阶段和 脚本管理页直接写入的修改。
- approved 的资源 JSON 和 confirmed 图片候选会进入草稿源包。
- 路由修复只写入 draft_module_json，原始模块基线保持不变。
- clear-results 不再重置 draft_module_json；Lua 页面提供独立的 Lua 草稿恢复入口。
- CHARX 导出会同步模块世界书镜像。
- 导出读取已保存的 draft_json、draft_module_json 和 draft source，不会自动改写原卡或远端平台。
- Lua、模板、控制引用、协议和正则完整性检查位于保存/导出路径，而不是只放在页面提示中。

### 必须明确或补齐的缺口

| 优先级 | 现象 | 边界后果 |
|---|---|---|
| P0 | apply 聚合主要按 review_status=approved，未统一判断 included | 用户明确排除的段落可能仍被保存 |
| P1 | confirmed OCR 没有对应的资源应用步骤 | UI 若显示“已确认”容易被误解为已进入卡片 |
| P1 | apply 入口未见统一活动任务锁或项目版本锁 | 保存可能与任务/直接编辑产生竞态 |
| P1 | 保存返回值未提供完整的通道清单和排除原因 | 用户无法确认 Lua、资源和其他页面修改是否已聚合 |
| P2 | 自动运行时别名或正则后处理失败可按确认继续 | 必须将“带失败保存”与“全部成功”明确区分 |
| P2 | 文件写入和数据库状态更新跨 storage/SQLite | 异常时可能产生孤儿草稿文件，需要清理和重试策略 |

## 9. 保存验收矩阵

发布前至少准备一张同时包含以下内容的 CHARX/RISUM 测试卡：

- 普通字段、问候语、世界书正文和世界书触发词；
- Lua 可见文本、Lua 语法错误行、正则规则、运行时名称目录和头像路由；
- 可见资源 JSON、图片资源、嵌入模块资源；
- 受保护宏、协议壳、按钮动作和资源路径。

执行以下测试：

1. 在不同页面分别修改每个通道，最后只点击一次保存；重新载入项目，逐项确认所有已批准/已确认的工件修改仍在。
2. 保留 draft Lua 修改，再批准卡片文本；保存后 Lua 修改不得消失。
3. 建立 pending/draft 候选；保存和导出均不得包含它们。
4. 建立 included=false 且 approved 的段落；系统必须拒绝这种冲突状态或明确不应用，不能静默写入。
5. 保存两次，输出字节、JSON、模块和资源哈希应保持幂等。
6. 修改 CHARX 卡片世界书和模块世界书；导出包中 card.json 与 module.risum 必须一致。
7. 确认 OCR 但不生成实际资源替换；界面和导出结果必须明确显示它仍是 OCR 候选。
8. 保存后执行 clear-results，确认翻译结果、卡片正文草稿和资源草稿被清除，但 Lua 草稿仍保留；再从 Lua 页面执行独立恢复按钮，确认只重置 draft_module_json 和 Lua 校验覆盖，不影响卡片正文、资源草稿和 original_module_json。
9. 活动任务期间通过 UI 和直接 API 同时尝试保存；不能产生混合版本。
10. 模型失败、正则失败、资源解析失败和 storage 写入失败时，项目不能伪造 ready，且失败原因可恢复。
11. 对照顶部保存、向导保存、保存并导出、脚本管理页安静保存和直接 API，验证结果相同。
12. 验证源文件哈希、API Key、日志和外部平台状态未被保存按钮意外修改。

## 10. 固定参数回归清单

以下内容只能在用户明确授权后变更，并且必须同步设置 UI、API 校验、数据库、调度器、导出命名和测试：

| 类别 | 当前语义 |
|---|---|
| 服务 | 默认 127.0.0.1:8787；Docker 容器监听地址与宿主映射是不同边界 |
| 上传 | WORKBENCH_UPLOAD_LIMIT_MB=0 表示不限；正整数表示 MiB 上限 |
| 数据库 | WORKBENCH_DB_WORKERS 默认 3，必须是大于 0 的整数 |
| 语言 | sourceLanguage=auto、fallbackLanguage=en、targetLanguage=zh-CN、languageBehaviorMode=target |
| 翻译批处理 | 默认并发 8、批量段落 8、批量字符 40000、超时 120 秒 |
| 范围 | all、core、standard、visible-scripts、all-visible、lua-only 六种既有值 |

“优化”不能缩小既有选项或扩大禁用范围，也不能只改前端显示而不改后端实际执行。

## 11. 其他部署和安全边界

- API 当前没有认证；默认安全前提是服务只绑定本机回环地址。改变 host、Compose 映射、反向代理或隧道后，必须重新提供认证、TLS、CSRF/来源控制和速率限制。
- 上传默认不限大小，仍受内存、解包、模型上下文和磁盘约束；部署应设置上限并监控 storage/SQLite。
- 模型、协议分析和图片 API 会接收卡片片段、协议样例、术语或图片；API 地址虽要求 HTTP(S)，但未限制主机和重定向，不能把它当作出站隔离。
- API Key 只能由后端读取；日志和错误体仍可能带用户内容，不能视为绝对脱敏。
- CHARX/RISUM 包内路径必须经过安全校验，不能穿越到 storage 根目录之外。
- 删除项目和清空结果是不可逆或难以恢复的操作，必须在用户可见说明中列出影响通道。

## 12. 最终执行原则

今后任何改动先回答四个问题，再写代码：

1. 这项数据是否真的改变最终卡片工件，还是只改变流程元数据？
2. 如果改变卡片，它的保存条件是 approved、confirmed、显式应用，还是其他状态？
3. 保存按钮是否会读取并合并它，重扫、重试、清空和导出是否会保留或清除它？
4. 失败、冲突、重复点击和直接 API 调用时，用户能否看到真实结果？

回答不完整的流程不得宣称已经接入保存。Lua、图片、OCR、资源 JSON、正则、路由修复只是不同的例子；真正不可越过的边界是“工件修改的归属、确认状态、聚合保存和可验证回退”。

本轮已按边界要求调整实现：路由修复只写 draft_module_json；clear-results 不再重置 draft_module_json；Lua 页面新增独立的“恢复原始 Lua 草稿”按钮。未修改原始卡片文件、备份或构建产物。
