# 同类漏翻面：受影响卡片清单

扫描范围：`data/storage/projects` 下全部 114 个已导入项目（charx / risum / png / json）；
其中 Risu 模块正则规则共 783 条。

判定方式：对每张卡跑一遍工作台自己的 `scanRisuModule(card, 'all')` / `scanCard(card, 'all')`，
取未被任何 segment 覆盖的字段；再剥掉 `<style>`、`<script>`、HTML 注释、URL 和 `{{…}}` CBS 宏外壳，
只统计剥完后仍残留 ≥2 个韩文/日文假名的字段。

## 结论

- 真正命中的只有 **module.regex[].out**，共 **39 处 / 10 个项目**。
- `card.customscript[].out`、`module.backgroundHTML`、`card.backgroundHTML`：剥掉 CSS/HTML 注释后**命中 0 处**。
  首轮粗筛曾报出 35 处 backgroundHTML，全部是 `<style>` 里的韩文注释，属误报，已剔除。
- 这 39 处**没有一处适合用"纯文本兜底"去修**：它们要么是 in/out 成对的词形校正，
  要么是宏外壳里夹着运行时比较值（翻译整个字段会直接破坏比较）。详见下方分组。

## 为什么这些不能靠"统一兜底"修

1. **词形校正对**：`in: 아셴트 → out: 아셴테`、`in: 역세계 → out: 반전세계` 这类，
   两侧都是源语言，作用是统一译名写法。中文卡里 `in` 根本匹配不到中文正文，规则本身已经失效；
   要修必须 **in/out 成对本地化**（给 `in` 追加中文并列项，同时把 `out` 换成对应中文名），
   这正是现有 `applyRisuRegexAlternativeProposals` 只做了一半的地方 —— 它只追加 `in` 的字面量。
2. **CBS 宏模板**：例如 SCHOOL-LIVE 的状态注释规则
   `{{#if {{equal::{{getvar::gks_panel_state_yuki}}::사망}}}}$1사망 / 영구 사망 고정{{/if}}`。
   其中 `사망` 既是**比较操作数**（不能动）又出现在 `$1사망 / 영구 사망 고정` 这段**可见替换文字**里。
   整字段翻译会把 `getvar` 的比较值一起翻掉，规则静默失效。
3. 现有设计已经把 `out` 定为**只读上下文**：`collectRegexLanguageEntries()` 把 `out` 读出来只是喂给模型判断 `in` 的并列项，
   写回路径 `appendRegexLiteralAlternatives()` 只改 `in`，从不重写 `out`。
   这是有意的安全边界，不是遗漏。

要覆盖这 39 处，需要的是一个独立功能（regex in/out 成对本地化 + CBS 外壳感知），
风险与工作量都和 trigger 文案扫描不是一回事。
