## 仍存在的状态不一致

### 1. 保存后撤回审核，引导和侧栏仍显示可导出

通过实际 API 完成翻译、全部审核、保存，然后将一条译文改回 pending。

结果：项目仍为 ready；页面同时显示“待人工审核 1”“已通过 1”和“审核稿已保存，可以继续导出”，流程条把审核标记为完成。导出内容重建正确，但用户会误以为本次审核已经全部完成。

位置：

- server/routes/api.ts:1897 更新片段审核状态，没有同步项目阶段。
- src/pages/workbench/components/workflow/GuidedWorkflow.tsx:286 直接按 ready 显示完成引导。

应让“已保存过草稿”与“当前还有待审修改”分别表达，待审数量不能被旧 ready 状态覆盖。允许部分导出时，也应明确说明只带出已审核部分。

### 2. 第二阶段失败，被“可以保存并导出”引导覆盖

合成任务状态：review_with_errors；正文 2 条均审核通过；第二阶段总计 2、完成 1、失败 1。

实际组件和浏览器都显示“审核已通过，可以保存并导出”，并声称“运行时名称别名已由翻译阶段处理”。失败状态仍在任务接口中。

位置：src/pages/workbench/components/workflow/GuidedWorkflow.tsx:250。

该分支只判断有没有待审核译文以及是否有已通过译文，未将第二阶段失败作为优先提示。应明确提示未完成适配并提供阶段 2 重试入口；是否允许部分导出应由具体校验结果决定，不能直接宣称适配已经完成。

### 3. 全部完成后重扫，要求执行一个没有内容可执行的翻译步骤

实际 API 完成并审核全部 2 条，再按相同范围重扫。译文与审核成果保留正确，但项目统一变成 scanned。

浏览器显示“待翻译”“扫描完成，选择翻译方式”和“开始翻译”；点击后仅跳转任务页并提示“当前翻译和阶段 2 均已完成，没有需要重复执行的内容”。

位置：

- server/application/scanning/scan-service.ts:169 无条件写 scanned。
- src/pages/workbench/components/workflow/GuidedWorkflow.tsx:179 按 scanned 直接引导翻译。
- src/features/translation/model/useTranslationTasks.ts:86 附近拦截重复启动。

应按当前范围真实待翻译、待审核和适配项决定下一步，而不是仅用最近一次操作名表示阶段。

### 4. 任务实际固定中文，但任务页显示跟随全局日文

把全局默认目标从 zh-CN 改为 ja 后，已创建项目仍为 zh-CN，任务持久化语言也是 zh-CN。浏览器项目头部显示 en → zh-CN，任务详情却显示“卡片语言设定：跟随 ja”。

位置：src/pages/workbench/WorkbenchPage.tsx:471 优先传入 settings.targetLanguage。

任务页应显示任务创建时固定的语言配置。只改用项目当前值也不足以准确展示历史任务的语言行为模式。

### 5. 暂停任务的第二阶段仍显示正在处理

对合成任务设置 paused，正文完成 2，阶段 2 完成 0/2。

实际 JobsPage 渲染同时包含“已暂停”“翻译中 2”和“正在处理 Lua 正则、关键词和剩余 2 个运行时名称”。

位置：src/pages/workbench/tabs/jobs/JobsPage.tsx:32、46、68、75。

该结论通过合成状态的实际组件渲染验证，未在本轮浏览器重新操作暂停流程。剩余数量不等于正在执行数量；阶段 2 的活动提示必须结合 queued/running/paused/cancelled/failed。

### 6. 上个项目的成功提示留在下一个项目

浏览器在“完成后重新扫描”项目点击开始，得到“当前翻译和阶段 2 均已完成”的提示；随后切换到“第二阶段失败”项目，该提示仍留在页面。

位置：src/pages/workbench/model/useWorkbenchFeedback.ts:8、32。提示为页面全局状态，仅运行新操作时清空，没有项目归属。
