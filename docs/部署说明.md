# 卡片翻译工作台：项目介绍与部署说明

本文面向从 GitHub 获取项目的使用者，介绍项目用途、功能边界和部署方式。

## 项目定位

卡片翻译工作台是一个独立运行的本地工具，用于导入角色卡或模块、提取可翻译内容、调用兼容 OpenAI Chat Completions 的模型、人工审核译文，并生成新的卡片文件。

工作台不依赖 RisuAI 才能运行，也不会自动修改其他应用中的卡片或聊天记录。默认只监听本机回环地址，适合个人电脑使用。

项目主要针对 RisuAI 模块（RISUM）和 CHARX 卡片开发，相关流程经过较充分测试。PNG、普通 JSON 等酒馆卡格式目前只提供基础兼容，测试覆盖不足；导入这类文件后，应在目标客户端实际打开导出结果并自行核对。

## 核心能力与边界

- 主要支持导入和导出 CHARX、RISUM；JSON、PNG 等酒馆卡格式提供基础兼容流程。
- 按范围扫描角色主体、世界书、问候语、脚本界面、Lua 提示词和资源 JSON 可见文本。
- 独立调度翻译任务，支持并发、批次、失败重试和任务进度查看。
- 在审核页对比原文、机器译文和人工定稿，审核通过后才应用到审核稿。
- 默认保护 Lua、正则、变量、协议外壳、路径、URL、ID、触发器和资源文件名。
- 保留世界书原始触发词，以追加别名方式写入目标语言关键词。
- 资源页支持 OCR 候选和图片编辑模型两种独立流程；不会自动覆盖原始图片。

机器翻译只产生草稿，不代表内容已经正确。导出前应检查高疑点字段、协议、脚本界面和资源引用。

项目没有登录鉴权，设计目标是单机使用，不应直接暴露到公网。第三方模型的可用性、费用和限流由服务商决定。

## 前置条件

任选一种运行方式：

- Docker：Docker Desktop（Windows）或 Docker Engine（Linux），以及 Docker Compose v2。
- 本地 Node.js：Node.js 22 或更高版本，以及 npm。

首次构建需要访问 npm registry 和 Docker 镜像仓库。验证版本：

```bash
docker version
docker compose version
node --version
npm --version
```

## 配置：先启动，再设置模型

部署阶段不需要先填写模型接口或 API Key。先按下面的 Docker 或 Node.js 步骤启动工作台，打开页面后点击左侧底部的“模型设置”，再填写模型配置。

页面里的“模型设置”可以配置：

- API Base URL 或完整 Chat Completions 接口地址。
- 模型名称和 API Key。
- 源语言、备用语言、目标语言、并发数和批次大小。
- 如需处理图片，再填写图片编辑 API 地址、模型和 API Key。

页面保存的这些设置由后端写入本地 SQLite，API Key 由使用者自行配置，浏览器不会展示密钥内容。`.env` 中的环境变量只用于部署参数，不会由启动流程写入模型设置或覆盖 SQLite；只有点击开始翻译、协议分析或图片处理时，工作台才会检查相应配置。

如果需要设置部署参数，可以在仓库根目录创建 `.env`。模型配置不通过 `.env` 预置或覆盖；`.env` 只保存在本机，切勿提交到 GitHub。

Windows PowerShell：

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
notepad .env
```

Linux：

```bash
[ -f .env ] || cp .env.example .env
nano .env
```

第一次使用可以保持 `.env.example` 中没有模型配置，启动后直接在页面“模型设置”里填写。模型、语言、并发、批次和图片设置不接受环境变量。

## 快速开始：Docker

在仓库根目录执行：

```bash
docker compose -f docker/compose.yml config
docker compose -f docker/compose.yml up -d --build
```

默认只绑定宿主机 `127.0.0.1:8787`，打开 `http://127.0.0.1:8787/`。

健康检查：

Windows PowerShell：

```powershell
Invoke-RestMethod http://127.0.0.1:8787/api/health
docker compose -f docker/compose.yml ps
```

Linux：

```bash
curl --fail --silent --show-error http://127.0.0.1:8787/api/health
docker compose -f docker/compose.yml ps
```

健康接口返回 `ok: true` 且容器状态正常后即可使用。

### 修改宿主机端口

端口冲突时，在 `.env` 中只修改宿主机端口：

```dotenv
WORKBENCH_BIND_PORT=18880
```

重新执行 `docker compose -f docker/compose.yml up -d`，随后访问 `http://127.0.0.1:18880/`。容器内部端口仍为 `8787`，不要改成 `0.0.0.0` 监听。

## 本地 Node.js 部署

本地生产构建会使用 `dist/` 和 `dist-server/`，不需要 Docker：

```bash
npm ci
npm test
npm run build
npm start
```

默认地址是 `http://127.0.0.1:8787/`。如需临时使用其他端口：

Windows PowerShell：

```powershell
$env:WORKBENCH_HOST = '127.0.0.1'
$env:WORKBENCH_PORT = '18880'
npm start
```

Linux：

```bash
WORKBENCH_HOST=127.0.0.1 WORKBENCH_PORT=18880 npm start
```

本地 Node.js 默认使用 `data/`，Docker 默认使用 Compose 命名卷。切换运行方式后看不到另一边的数据是预期行为；迁移前请先备份。

## 使用操作流程

部署完成后，建议先配置模型，再按以下顺序处理卡片：

1. 在左侧“模型设置”填写模型接口、模型名和 API Key，并选择源语言、目标语言、并发和批次参数。
2. 导入 CHARX、RISUM、PNG 或 JSON 卡片；原始导入内容会保留，不会直接覆盖原文件。
3. 在“概要”确认卡片格式、字段、世界书、脚本、Lua、协议和资源数量是否识别正常。
4. 在翻译范围下拉框中选择内容。默认“全部翻译”适合完整处理可见文字、世界书、脚本界面、Lua 提示词和资源 JSON 可见文字。
5. 先扫描字段，再开始翻译；大卡先用较小的并发和批次确认流程稳定。
6. 在“任务”页处理失败批次。遇到保护占位符、协议结构或接口错误时，应先看失败原因再重试。
7. 在“审核”页对照原文、机器译文和人工定稿，优先检查高疑点字段、协议、Lua、脚本按钮和世界书触发词。
8. 生成审核稿后导出文件，并在目标客户端实际打开验证。PNG、普通 JSON 等酒馆卡目前测试覆盖有限，必须额外检查主体、世界书、脚本和资源引用。

CHARX 和 RISUM 是本项目的主要测试对象，但仍建议在导出前保留原文件并完成一次实际回验。

## 环境变量参考

`.env` 只用于部署参数，例如监听地址、端口、数据目录和上传限制。`TRANSLATION_*` 和 `IMAGE_EDIT_*` 环境变量不再受支持；模型、语言、并发、批次和图片设置只能在页面“模型设置”中保存到 SQLite。

| 变量 | 作用 | 默认值 |
| --- | --- | --- |
| `WORKBENCH_HOST` | 本地 Node.js 监听地址 | `127.0.0.1` |
| `WORKBENCH_PORT` | 应用内部监听端口 | `8787` |
| `WORKBENCH_BIND_PORT` | Docker 宿主机端口 | `8787` |
| `WORKBENCH_UPLOAD_LIMIT_MB` | 单个上传大小；`0` 表示不额外限制 | `0` |
| `WORKBENCH_DB_WORKERS` | SQLite Worker 数量 | `3` |
| `WORKBENCH_DATA_DIR` | 数据目录 | `data` |
| `WORKBENCH_DB_PATH` | SQLite 文件路径 | `data/workbench.sqlite` |
| `WORKBENCH_WEB_DIR` | 前端构建目录 | `dist` |

并发和批次越大，内存占用、接口费用和限流风险越高。大卡建议从较小的并发与批次开始。

## 数据、停止、更新与备份

Docker Compose 使用命名卷 `workbench-data` 保存 SQLite、上传文件、翻译草稿、会话临时文件和 OCR 缓存。

停止服务但保留数据：

```bash
docker compose -f docker/compose.yml down
```

重新构建并启动：

```bash
docker compose -f docker/compose.yml up -d --build
```

查看日志：

```bash
docker compose -f docker/compose.yml logs --tail=200
```

只有确认不再需要本地数据时，才执行 `docker compose -f docker/compose.yml down -v`；该命令会删除 Compose 数据卷。

备份前先停止工作台，避免 SQLite 正在写入。

Windows PowerShell：

```powershell
New-Item -ItemType Directory -Force backups | Out-Null
docker compose -f docker/compose.yml down
docker run --rm -v card-translation-workbench_workbench-data:/source:ro -v "${PWD}\backups:/backup" alpine:3.20 tar czf /backup/workbench-data.tgz -C /source .
```

Linux：

```bash
mkdir -p backups
docker compose -f docker/compose.yml down
docker run --rm -v card-translation-workbench_workbench-data:/source:ro -v "$PWD/backups:/backup" alpine:3.20 tar czf /backup/workbench-data.tgz -C /source .
```

备份可能包含模型密钥、上传卡片和翻译内容，应使用私密存储，不能提交到 GitHub。

## 安全注意事项

- 默认监听和端口映射都应保持在 `127.0.0.1`，不要直接暴露到公网。
- 当前工作台没有登录鉴权；远程使用时应在可信反向代理后增加认证、TLS 和访问控制。
- `.env`、SQLite、数据卷、日志、备份和导入卡片都可能含有密钥或私人内容。
- API Key 必须在页面“模型设置”中自行配置，由后端写入本地 SQLite；前端不会展示密钥内容。不要把密钥写入 `.env`、前端代码、提交记录或截图。
- 处理陌生卡片前先备份，导出前检查协议、Lua、正则、世界书触发词和资源引用。

## 常见问题

### 页面打不开

查看容器状态和日志，确认访问端口与 `WORKBENCH_BIND_PORT` 一致：

```bash
docker compose -f docker/compose.yml ps
docker compose -f docker/compose.yml logs --tail=200
```

### 翻译请求失败

检查 API Base URL、模型名、目标语言和密钥是否正确，确认服务商允许当前模型使用 Chat Completions。不要把完整密钥粘贴到日志、Issue 或聊天中。

### 导入大卡或扫描时内存不足

解包、资源扫描和 SQLite 都会占用内存与磁盘。设置合理的 `WORKBENCH_UPLOAD_LIMIT_MB`，降低并发、每批段落数和每批字符数，并清理不再需要的旧会话或缓存。

### 切换 Docker 和本地 Node 后数据不一致

两种运行方式默认使用不同的数据存储。先确认当前服务方式，再从对应的数据目录或 Compose 数据卷恢复备份；不要在服务运行时直接复制 SQLite 文件。

### Linux 无法写入数据

确认 Docker Engine 正常运行、当前用户有权限访问 Docker socket，并确保磁盘空间和 inode 充足。不要通过开放公网端口来绕过权限问题。

### 需要重新开始

先导出或备份需要保留的结果，再执行 `docker compose -f docker/compose.yml down -v`。该操作会删除 Docker 数据卷，无法由工作台撤销。
