> `npm test` 269/269 通过，`npm run build`（含三份 tsconfig 的 typecheck）通过。

## 一、结论先说

### 1. 这张小圆卡的正则不是工作台译坏的

用工作台自己的扫描/校验函数对同一张卡（08-30 翻译前 vs 线上当前）跑实测：

| 检查项 | 结果 |
| --- | --- |
| `scanCard(card, 'all')` 是否把 `customscript[41]/[42].in` 当成可翻译段 | **否**（0 段） |
| `risuControlReferences()` 在 `customscript` 下的锚点数量 | **0**（全部 483 个锚点都在 `triggerscript` 的 Lua 里） |
| `applyRisuRegexAlternativeProposals` / `applyRisuRegexCoverageProposals` 能否改到卡片 `customscript` | **不能**：两者都要求 `Array.isArray(module.regex)`，即只作用于 **Risu 模块（.risum）的 `regex` 数组** |
| `collectRegexLanguageEntries()`（阶段 2 入口）遍历的对象 | 同样是 `originalModule.regex`，**不含卡片 `customscript`** |
| `validateRisuControlReferences(翻译前, 线上)` 是否报出量词改动 | **否**（0 条 issue，见第三节缺口 B） |

卡片 `customscript` 的三层保护是闭合的：

1. `protectedPatterns()` 含 `/<\/?[^<>\n]{1,240}>/g`、`/\{\{[\s\S]*?\}\}/g`，正则语法整体处于保护态；
2. `isScriptPath()` / `isGenericProtectedPath()` 把 `customscript` 路径挡在翻译范围外；
3. `scanCard` 对脚本路径只调 `extractVisibleText()`，只抽 `{{button::}}`、HTML 属性、`>文字<` 三类**可见文字**，并要求 `!/<|>/`。

所以这次线上卡片的改动最可能是**人工编辑**留下的（站内插件 `card_cn_translator` 的字段抽取同样够不到正则 `in`）。

### 2. 但工作台存在一个**会生成同款破坏**的实测缺陷（模块 `regex`）

`applyRisuRegexCoverageProposals()` 对**运行期规则**（`editdisplay` / `editoutput`）的落地守卫用错了：
它只调用宽松的覆盖度检查，从不调用严格的结构检查。实测结果是 ——
**把 `[ \t]+` 改成 `[ \t]*` 的完整 pattern 替换会被直接接受**（复现见第三节缺口 B）。

也就是说：卡片这次没被工作台打坏（因为工作台够不到 `customscript`），
但**如果同样的规则存在于模块 `regex` 里，工作台就会打坏它**。

> 两句话总结：
> **这次事故的修复价值在卡片本身（已完成）；工作台是清白的；但工作台自身有一个必修缺陷，外加一个 `customscript` 盲区。**

## 二、工作台现在到底怎么处理正则

### 阶段划分

- **阶段 1（正文翻译）**：`scanCard` 产段 → 模型翻译 → `validateRisuControlReferences` 校验。正则 `in` 不产段。
- **阶段 2（Lua 正则语言适配）**：`collectRegexLanguageEntries()` → 模型 → `applyRisuRegexCoverageProposals()` / `applyRisuRegexAlternativeProposals()`。**只对 `module.regex` 生效。**

### 两种提案模式（`server/scheduler.ts` 系统提示词）

| 模式 | 允许的改动 | 落地校验 |
| --- | --- | --- |
| `sample` | 只能用 `anchorAlternatives` + `additions`，**只能追加普通文字字面量**，不得含正则语法（`\`、`|`、括号、方括号、量词、锚点、换行） | `appendRegexLiteralAlternatives()`：只往既有非捕获组尾部追加 `\|字面量`，**完全不碰前后缀** |
| `coverage` | 可返回**完整 pattern**，明确允许改"空格/制表符的必需性/可选性、量词、零宽断言、分组" | `applyRisuRegexCoverageProposals()` → `isSafeRegexLanguageAdaptation()` |

`coverage` 模式的落地门槛（`card.ts:790`）：

```
候选非空、≤4000 字符、无换行
能被 new RegExp 编译
捕获组数量与原文一致
原文在"翻译前卡片"上的命中数 > 0
候选在"翻译前卡片"上的命中数 ≥ 原文命中数
已有并列项必须全部保留（防止两阶段互相回退）
```

### 关键：`editdisplay` / `editoutput` 规则被当作"运行期规则"降级处理

```
dynamicDisplay     = type==='editdisplay' && out 只由 $1..$n 与换行组成
runtimePostprocess = type==='editoutput' && 有 out
runtimeRule        = dynamicDisplay || runtimePostprocess
```

`collectRegexLanguageEntries()` 里 `runtimeRule = true` 时：
`sourceSamples` / `coverageRecords` 置空 → **规则仍旧会进条目、仍旧会发给模型**，
只是样本与覆盖度证据为空。

真正的问题在落地端（见第三节缺口 B）：
`isSafeRegexLanguageAdaptation()` 里 `originalMatches <= 0 → return false`，
运行期规则在静态卡片文本上命中数必然为 0，所以它**注定返回 false**，
但 `applyRisuRegexCoverageProposals()` **并没有调用它之外的严格结构校验**
（`isSafeRisuDisplayFormattingRegexChange()` 只在"人工逐条预览"的 API 路径里用到），
于是完整 pattern 替换畅通无阻。

## 三、实测暴露的两个覆盖缺口

### 缺口 A — 卡片 `customscript` 的正则完全没有语言适配

`customscript` 是**普通角色卡最大的正则面**（这张卡 70 条）。现在：

- 不进阶段 2（只认 `module.regex`）；
- 翻译阶段不产段；
- 因此**没有任何"目标语言并列项"能力**。

后果：卡片正则里写死的源语言触发词（如 `하고|하는|라고`）在译成中文后**永远不会被补充中文等价项**。这张卡现在看到的 `的|说|说道|…` 就是人工补的——本该由工具做的事，靠人手动补，也就更容易补错（本次事故正是这一类改动没被任何校验兜住）。

另外 `lua-management.ts` 的 `regexRules` 来自 `controlReferences`，而 `risuControlReferences` 对 `customscript` 产不出锚点（`literalRegexSource()` 遇到 `*+?()[]{}|` 直接返回 null），所以 **Lua 管理页也看不到这 2 条规则**（实测 `regexRules.length = 0`，尽管卡片有 70 条 customscript）。

### 缺口 B — 【已实测可利用】模块的 `editdisplay` / `editoutput` 正则可以被子串替换

**这是真正的代码级缺陷，不是理论推测。** 用这张卡自带的规则做实测（`tmp/coverage-probe.ts`）：

```
rule type            : editdisplay
isDisplayFormatting  : true
original has [ \t]+ : true
candidate has [ \t]*: true

applyRisuRegexCoverageProposals changes: [{"pathLabel":"模块.regex.0.in","addedAlternatives":[]}]
module.regex[0].in === brokenPattern  : true
=> a full-pattern (non-additive) rewrite of an editdisplay rule is: ACCEPTED
```

即：**工作台自己就能生成本次事故的同款破坏**（`[ \t]+` → `[ \t]*`），只要目标规则是模块 `regex` 里的 `editdisplay`。

成因是 `applyRisuRegexCoverageProposals()` 的兜底顺序（`card.ts:717`）：

```ts
if (!isSafeRegexLanguageAdaptation(entry.in, proposal.pattern, originalCard ?? {})) return;
```

它用的是**宽松的覆盖度守卫**（`isSafeRegexLanguageAdaptation`：可编译 + 捕获组数相同 + 原卡命中数不减少），
而**根本没有调用** `isSafeRisuDisplayFormattingRegexChange()`（那个严格的结构校验）。
只改量词时命中数完全不变，于是宽松守卫放行。

`runtimePostprocess`（`editoutput`）同理。

加剧因素：`server/scheduler.ts` 的 `coverage` 模式系统提示词明确告诉模型可以改

> "空格或制表符的必需性/可选性、……、为此必要的零宽断言、分组和**量词**"

也就是说：模型被**鼓励**做这类改动，而落地校验对运行期规则又退化成宽松覆盖度检查。

补充：`validateRisuControlReferences(翻译前, 线上)` 对这种改动返回 **0 条 issue**（`dynamicDisplay` 分支直接 `continue`），
所以**导出前也不会有任何警告** —— 两道闸门同时放行。

## 四、改进方向（按性价比排序）

### 方向 1：给 `customscript` 正则补上"只追加、可回退"的语言适配（推荐）

复用现有 `sample` 模式的机制，但把作用域从 `module.regex` 扩到 `card.customscript[].in`：

1. **产锚点**：为 `customscript[].in` 生成参考对象（需要把 `literalRegexSource()` 的"整串字面量"要求放宽到"可枚举非捕获组"，或新增一条 `regex-group-anchor` 提取路径），只用于**定位并列组**，不用于翻译。
2. **只追加**：复用 `appendRegexLiteralAlternatives()`，改动仅限往既有非捕获组尾部追加 `\|中文词`，**不触碰量词、分组、锚点、断言**。
3. **强校验**：追加后必须
   - `countCapturingGroups` 不变；
   - 所有原并列项仍在（顺序不变）；
   - 在**原卡**上命中数 ≥ 原命中数；
   - 追加项逐个过 `isSafeRegexLiteral`（禁正则元字符）。
4. **可回退**：把"追加了哪些并列项"写进审核条目，审核页可一键撤销。
5. **补测试**：`tests/` 增加断言 —— 追加式改动只能增加 `|字面量`，量词/断言/分组字节级不变。

> 直接收益：中文卡不再需要人工补中文触发词；本次事故这类"顺手改量词"的改动在结构上就不可能发生。

### 方向 2：【必修】堵住运行期正则的完整 pattern 替换通道

在上面实测确认为真之后，这条从"提示"升级为"必修"：

**做法**：`applyRisuRegexCoverageProposals()` 遇到 `isRisuDisplayFormattingRegexRule(entry)` 或
`isRisuOutputPostprocessRegexRule(entry)` 为真时，**直接拒绝完整 pattern**，只允许走
`applyRisuRegexAlternativeProposals()`（纯追加 `|字面量`）；`additions` 已由
`isSafeRegexLiteral()` 禁止 `\ ( ) [ ] { } * + ? | ^ $` 与换行，是结构安全的。

```ts
// card.ts / applyRisuRegexCoverageProposals 内，替换现有单行守卫
const rule = module.regex?.[index] as Record<string, unknown>;
if (isRisuDisplayFormattingRegexRule(rule) || isRisuOutputPostprocessRegexRule(rule)) {
  continue; // 运行期规则只允许追加式改动，绝不接受完整 pattern 替换
}
if (!isSafeRegexLanguageAdaptation(entry.in, proposal.pattern, originalCard ?? {})) return;
```

**同时**在 `server/scheduler.ts` 的 `coverage` 提示词里删掉/收紧"量词"这项授权，改为：

> 运行期规则（`dynamicDisplay` / `runtimePostprocess`）只允许追加并列项，不得返回完整 pattern；
> 其它规则若必须改量词，需在 `reason` 中说明为何运行期行为不变。

**验收测试**（放 `tests/card.test.ts`）：

1. 对 `editdisplay` 规则提交"仅改量词"的完整 pattern → 必须被拒绝、`entry.in` 不变；
2. 对 `editdisplay` 规则提交追加式 `additions` → 允许，且量词/断言/分组字节级不变；
3. 对普通规则提交合法覆盖候选 → 仍允许（不误伤现有能力）。

### 方向 3：给 `editdisplay` / `editoutput` 加"量词与边界变更"审核警告

方向 2 堵住的是工作台自己的写入通道；人工编辑仍然可能踩坑，所以再加一层体检：

在 `validateRisuControlReferences()` 的 `dynamicDisplay` / `runtimePostprocess` 分支里，
不再直接 `continue`，而是补一条**结构指纹**比较，发现下列差异时产出一条**审核警告（不阻断）**：

- 量词：`*` `+` `?` `{m,n}` 的种类/位置变化
- 字符类：`[ \t]`、`\s` 这类边界类的增删
- 断言：`(?=)` `(?!)` `(?<=)` `(?<!)` 的增删
- 转义序列变化

理由：这类改动在静态卡片文本上**命中数完全不变**，只能用指纹发现，交给人工确认即可。
本次事故的改动会被这条直接标出来。

### 方向 4：导出前做一次"协议回归"（面向结果）

导出卡片前，用卡片自己的 `customscript` 对**开场白 + 最近若干条聊天记录**跑一遍 `editdisplay`，统计：

- 输入里 `<img="…">` 这类协议标签的数量；
- 输出里被成功转换的数量；
- 差值 > 0 时在导出报告里列出**未被任何规则消费的协议标签**（本次事故会在导出前就报出"13 个 `<img=…>` 没有任何规则处理"）。

实现成本低（`editdisplay` 是纯字符串变换，不需要浏览器），且不依赖静态命中数。
这一条对**卡片 `customscript`** 尤其重要，因为方向 1 未落地前它在工作台里是完全的盲区。

### 方向 5：文档与提示词

- 在 `docs/` 明确写清工作台对正则的**真实边界**：
  - 卡片 `customscript` 正则：不产段、不锚定、不校验（盲区）；
  - 模块 `module.regex`：可追加并列项，运行期规则目前还能被完整 pattern 替换（方向 2 修复前）。
  避免以后再花时间怀疑到错误的方向。
- `server/scheduler.ts` 的 `coverage` 提示词按方向 2 收紧量词授权。

## 六、实施记录（2026-09-12）

四项改进已全部落地。设计原则：**保留"给正则追加中文触发词/翻译"的能力，保留人工对比能力，不引入回归。**

### P0 方向 2 — 堵住运行期正则的完整 pattern 替换

- `server/domain/card/card.ts`
  - 新增 `isRuntimeScopeRegexRule(rule)` = `isRisuDisplayFormattingRegexRule || isRisuOutputPostprocessRegexRule`。
  - `applyRisuRegexCoverageProposals()` 对运行期规则**直接跳过**，不再接受完整 pattern。
- `server/scheduler.ts`：运行期 payload 的 `runtimeRequirement` 明确禁止改量词/字符类/断言/分组，只允许 `anchorAlternatives + additions`。
- **保留的能力**：运行期规则仍可走 `applyRisuRegexAlternativeProposals()` 追加 `|中文词`（纯字面量，`isSafeRegexLiteral` 已禁正则元字符）。
- 测试：`tests/card.test.ts` 新增 3 条（拒绝改量词 / 仍可追加 / 非运行期规则不受影响）。

### P1 方向 3 — 运行期正则结构指纹警告

- `regexStructureFingerprint(pattern)`：抽取量词、字符类、转义、零宽断言四类指纹。
- `collectRisuRuntimeRegexStructuralDrift(original, draft, rootLabel)`：对比后产出
  `RisuRegexStructuralDrift[]`（`kind` / `removed` / `added` / 中文 `message`）。
- 接入面：`lua-management.ts` → `LuaManagementReport.issues`，`kind: 'regex-drift'`、`blocking: false`
  → 自动出现在 `LuaExportIssues.tsx` 与 `warningCount`。
- **人工对比保留**：`LuaExportIssues.tsx` 的"打开规则"按钮现在对 `regex-drift` 也生效（原来只对 `control`），
  点进去就是逐条的人工定稿编辑器。
- 前端类型：`LuaManagementIssue.kind` 增加 `'regex-drift'`；`LUA_ISSUE_LABELS` 增加「运行期正则结构」。
- 测试：`tests/card.test.ts` 2 条 + `tests/lua-management.test.ts` 1 条。

### P1 方向 1 — 卡片 `customscript` 追加式语言适配

- `collectCardCustomscriptRegexEntries(originalCard, draftCard)`（`schedule.ts`）：为卡片 `customscript[].in`
  产出语言条目，`pathLabel = 卡片.customscript.N.in`，`origin: 'card'`；运行期规则同样不带静态样本。
- `applyCardCustomscriptRegexAlternatives(card, proposals)`（`card.ts`）：**只追加**，复用
  `appendRegexLiteralAlternatives()`，不碰量词/分组/锚点/断言/`out`。
- 歧义守卫 `isAmbiguousRegexAlternativeAnchor()`：命中多个并列组、锚点是同级字面量的前缀（`说` vs `说道`）、
  锚点不存在 → **一律不改**，留给人工编辑器，避免静默改变匹配范围。
- 阶段 2 编排：模块条目 + 卡片条目同一轮模型调用；写回时用 `updated_at` CAS，卡片有改动才一并更新 `draft_json`，
  与模块写回原子同步。
- **保留的能力**：这正是"给正则增加中文触发词"的能力，只是现在**结构上不可能**顺手改坏量词。
- 测试：`tests/scheduler.test.ts` 新增 4 条（条目收集 / 只追加 / payload 标记 / 歧义守卫）。

### P2 方向 4 — 导出前协议回归

- `collectRisuUnconsumedProtocolTags(card, samples)`（`card.ts`）：用卡片自己的 `editdisplay` 规则跑一遍文本，
  统计"发出多少伪标签 vs 跑完后还剩多少伪标签"。
- **能同时抓到两种失效**：标签原样残留（渲染成文字）与被上游规则改坏后残留（`<img="\n名字">`），后者正是本次事故的形态。
- 保守性：跳过 `<cbs>` 规则与 `@@` 指令规则；**一条都没匹配就完全静默**，避免把无法模拟的卡片变成噪声源。
- 接入面：`lua-management.ts` 对开场白、备用开场白、最近 3 个聊天各取最后 6 条消息做样本，
  `kind: 'protocol-regression'`、`blocking: false`。
- 测试：`tests/card.test.ts` 2 条 + `tests/lua-management.test.ts` 1 条。

### 验证结论（对真实小圆卡）

| 检查 | 线上（坏） | 修复后（好） |
| --- | --- | --- |
| 结构指纹漂移 | **2 条**（`卡片.customscript.41/42.in`，`[ \t]*` → `[ \t]+`） | 0 条 |
| 协议回归 | **1 条**（13 个 `<img="…">` 未被消费） | 0 条 |
| 追加式适配 | 量词保持 `[ \t]+`、断言与 `out` 逐字节不变，仅追加 `\|说\|说道` | 同 |

### 未采纳的两项

- **不在 `validateRisuControlReferences()` 里发警告**：该函数的结果被导出/应用当作**阻断项**消费，
  在里面加警告会误伤 `tests/card.test.ts:448` 这类正确放行的用例。改用独立的
  `collectRisuRuntimeRegexStructuralDrift()`，语义更准，也不动既有阻断契约。
- **不给导出成功路径加新字段**：目前导出没有成功态报告对象，加字段是较大的接口变更；
  P2 的结果通过 `GET /lua/diagnostics` 到达界面即可。

### 已知限制

- 协议回归是**静态模拟**：需要 `<cbs>` 展开的规则被跳过，因此少数卡片可能完全静默（这是有意选择）。
- 若某条规则在自己的替换结果里改坏了标签，会按"被改坏的残留"报告，`tag` 字段展示的是残留实际形态。
- 结构指纹里的字符类是按文本比较的，所以"给字符类补一个目标语言范围"也会提示——这是**咨询性**提示，不阻断。
